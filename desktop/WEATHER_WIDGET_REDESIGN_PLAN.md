# PinWall 桌面天气插件改造规划

## 1. 文档目标

本文档用于规划 PinWall 现有桌面天气模块的改造方案，目标是将当前的简版天气卡片升级为一套更完整的天气体验，满足以下三个核心诉求：

1. 默认状态展示图 1 这种简洁的天气卡片。
2. 点击默认卡片后，弹出图 2 这种天气详情窗口。
3. 点击图 2 右上角按钮后，弹出图 3 这种城市选择侧栏，并支持选择城市、搜索城市、切换城市。

本文档只做产品与技术规划，不直接进入实现代码阶段。

---

## 2. 当前现状梳理

结合现有代码，当前天气能力并不是一个独立的 Widget，而是主桌面右侧边栏中的一个内置组件。

### 2.1 当前实现位置

- 主桌面挂载入口：`desktop/src/pages/Wall.tsx`
- 天气组件：`desktop/src/components/WeatherCard.tsx`
- 天气服务：`desktop/src/services/weatherService.ts`
- 天气提醒 Hook：`desktop/src/hooks/useWeatherCare.ts`
- 设置入口：`desktop/src/components/SettingsPanel.tsx`
- 样式定义：`desktop/src/App.css`

### 2.2 当前行为

当前天气模块具备的能力：

- 当 `weatherCareEnabled` 开启时，在主桌面右侧边栏显示 `WeatherCard`。
- 若设置中填写了 `weatherCity`，则按手动城市查询天气。
- 若没有填写 `weatherCity`，则尝试自动定位当前城市。
- 展示内容较轻量，只包含：
  - 当前城市
  - 当前温度
  - 当前天气描述
  - 未来 7 天基础预报
- 每 30 分钟自动刷新一次天气数据。

### 2.3 当前实现的局限

当前能力和目标设计之间存在明显差距：

1. 只有一个卡片层级，没有“默认卡片 -> 详情窗口 -> 城市侧栏”三层交互。
2. 只支持单城市配置，不支持多城市收藏和快速切换。
3. 没有小时级天气展示。
4. 没有更丰富的当前天气信息，如最低/最高温、湿度、风速、气压等。
5. 没有独立的详情弹层状态管理。
6. 没有城市搜索候选列表，也没有最近使用城市、收藏城市的概念。
7. 现有视觉风格是深色玻璃态卡片，与参考图中的浅色大面板风格差异较大。

## 3. 改造目标定义

## 3.1 产品目标

把现有天气模块改造成一个“桌面轻量入口 + 详情面板 + 城市管理侧栏”的三级天气体验。

### 3.2 目标体验

#### 图 1：默认展示态

用户在桌面上默认看到一个小尺寸天气卡片，信息简洁，优先承担“抬眼即看”的作用。

建议展示信息：

- 城市名
- 当前温度
- 当前天气图标
- 未来 3 天简要预报

目标特点：

- 默认态体积小
- 信息密度低
- 视觉上适合长期停留在桌面
- 一眼能看到“当前怎么样 + 接下来几天大概如何”

#### 图 2：点击后的详情态

当用户点击默认卡片后，打开一个较大的天气详情窗口。

建议展示信息：

- 城市名
- 当前温度
- 当前天气现象
- 今日最低/最高温
- 风向、风速
- 湿度
- 气压
- 未来 24 小时预报
- 未来 7 天预报

目标特点：

- 承担完整天气浏览功能
- 信息结构清晰
- 支持更高频的短时查看
- 保持桌面产品“轻量、不打断”的原则

#### 图 3：城市管理态

当用户点击图 2 右上角按钮时，打开城市选择侧栏。

建议具备的能力：

- 搜索城市
- 从候选列表中选择新城市
- 显示已保存城市列表
- 一键切换当前主城市
- 支持新增城市
- 后续可扩展删除城市、置顶城市、最近访问城市

目标特点：

- 用户不需要进入设置页就能完成天气城市切换
- 多城市查看路径清晰
- 为后续做“常驻城市列表”打基础

## 4. 设计原则

### 4.1 保持桌面第一性

PinWall 是桌面应用，不是纯天气 App，因此天气模块要强调：

- 常驻但不喧宾夺主
- 展开查看时信息完整
- 收起后尽量克制
- 尽量减少跳转到设置页的操作负担

### 4.2 分层交互

三层体验必须职责清晰：

- 图 1：快速读信息
- 图 2：完整看天气
- 图 3：管理城市

不要把所有能力都塞进图 1，否则会破坏桌面端轻量感。

### 4.3 先内置模块升级，不急着迁移到 Widget 系统

当前天气能力位于 `WeatherCard.tsx`，并未接入正式 Widget 安装体系。此次改造建议优先继续作为“内置天气模块”迭代，而不是立刻迁移成独立 Widget，原因如下：

- 当前已有入口和数据链路，改造成本更低。
- 需求重点是交互升级，不是开放式 Widget 生态。
- 如果过早迁移到 Widget 体系，会额外引入 manifest、权限、bridge、iframe 通信等复杂度。
- 等天气交互成熟后，再评估是否封装成官方 Widget 更稳妥。

结论：

- 第一阶段：沿用内置天气模块实现。
- 后续阶段：如需市场化/可安装化，再抽象为官方天气 Widget。

## 5. 目标信息架构

### 5.1 视图层级

建议拆成三个 UI 实体：

1. `WeatherCardCompact`
   - 对应图 1
   - 默认常驻在侧边栏或桌面固定区域
2. `WeatherDetailPanel`
   - 对应图 2
   - 点击默认卡片后打开
3. `WeatherCityDrawer`
   - 对应图 3
   - 点击详情右上角按钮后打开

### 5.2 状态关系

建议使用如下 UI 状态：

- `isWeatherDetailOpen`
- `isWeatherCityDrawerOpen`
- `activeWeatherCityId`
- `weatherSearchKeyword`
- `weatherSearchResults`
- `savedWeatherCities`

### 5.3 推荐交互路径

主路径如下：

1. 用户在桌面看到默认天气卡片。
2. 用户点击卡片。
3. 打开天气详情窗口。
4. 用户点击右上角城市按钮。
5. 打开城市侧栏。
6. 用户搜索并选择新城市。
7. 当前城市切换，详情窗口与默认卡片同时刷新。
8. 新城市写入本地保存列表。

## 9. 数据模型改造规划

当前 `Settings` 中只有：

- `weatherCareEnabled?: boolean`
- `weatherCity?: string`

这个结构只适合“单城市字符串”模式，不适合图 3 的城市管理。

### 9.1 建议新增数据结构

建议将天气配置升级为独立对象，例如：

```ts
interface WeatherCityItem {
  id: string;
  name: string;
  lat: number;
  lon: number;
  country?: string;
  admin1?: string;
  isAutoDetected?: boolean;
  lastViewedAt?: number;
  addedAt: number;
}

interface WeatherPreferences {
  enabled: boolean;
  activeCityId: string | null;
  cities: WeatherCityItem[];
  useAutoDetectedCityWhenEmpty: boolean;
  lastAutoDetectedCity?: WeatherCityItem | null;
  compactDays: number;
}
```

### 9.2 设置层建议

可以在 `Settings` 中新增：

```ts
weather?: WeatherPreferences;
```

并逐步废弃旧字段：

- `weatherCity`
- 后续 `weatherCareEnabled` 也可并入 `weather.enabled`

### 9.3 兼容迁移策略

读取旧设置时执行迁移：

1. 若存在旧 `weatherCity`，则自动转成 `cities[0]`。
2. `activeCityId` 指向迁移出来的第一个城市。
3. 若旧用户没有城市，则保持空列表，并允许自动定位填充。
4. 老字段保留一段版本周期，避免历史配置异常。

## 10. 天气服务层改造规划

当前 `weatherService.ts` 支持：

- 城市转经纬度
- 当前天气
- 7 日天气
- 自动定位

但还不够支持图 2 和图 3 的完整体验。

### 10.1 需要补充的服务能力

#### 1. 城市搜索服务

新增：

```ts
searchCities(keyword: string): Promise<WeatherCitySearchResult[]>
```

用于图 3 搜索输入框的候选城市列表。

#### 2. 小时级天气接口

新增：

```ts
getHourlyWeatherByCoords(coords: WeatherCoords): Promise<HourlyWeatherData[]>
```

用于图 2 的未来 24 小时展示。

#### 3. 聚合接口

建议封装统一接口：

```ts
getWeatherBundleByCity(...)
getWeatherBundleByCoords(...)
```

返回：

- 当前天气
- 今日高低温
- 未来 24 小时
- 未来 7 天
- 扩展指标（湿度、风速、风向、气压）

这样 UI 层只请求一次聚合数据，避免多个请求散落在组件中。

### 10.2 建议的返回结构

```ts
interface WeatherBundle {
  location: {
    city: string;
    lat: number;
    lon: number;
  };
  current: {
    temperature: number;
    weatherCode: number;
    description: string;
    humidity?: number;
    windSpeed?: number;
    windDirection?: string;
    pressure?: number;
    temperatureMin?: number;
    temperatureMax?: number;
  };
  hourly: Array<{
    time: string;
    temperature: number;
    weatherCode: number;
    description: string;
  }>;
  daily: Array<{
    date: string;
    temperatureMin: number;
    temperatureMax: number;
    weatherCode: number;
    description: string;
  }>;
}
```

### 10.3 缓存策略

建议增加本地内存缓存，避免频繁请求：

- 当前活跃城市天气：缓存 10 到 15 分钟
- 已保存城市简版摘要：缓存 30 分钟
- 城市搜索结果：缓存 5 分钟

### 10.4 错误降级

需要明确以下降级行为：

- 城市搜索失败：提示“搜索失败，请稍后重试”
- 详情天气失败：显示空态和重试按钮
- 某个已保存城市摘要失败：仅该卡片降级，不影响其他城市
- 自动定位失败：保留上次城市，不强制清空

## 12. 关键交互流程设计

### 12.1 首次进入

1. 用户首次打开应用。
2. 若天气模块开启但没有保存城市：
3. 尝试自动定位当前城市。
4. 定位成功：
   - 自动生成一个默认城市项
   - 作为当前活跃城市
   - 显示图 1
5. 定位失败：
   - 图 1 显示空态或默认文案
   - 引导用户点击后在图 3 搜索城市

### 12.2 查看详情

1. 用户点击图 1 默认卡片。
2. 打开图 2 详情窗口。
3. 若当前城市数据未命中缓存，则发起聚合请求。
4. 成功后渲染当前天气、24 小时、7 天预报。

### 12.3 切换城市

1. 用户点击图 2 右上角按钮。
2. 打开图 3 城市侧栏。
3. 用户搜索“上海”。
4. 展示城市候选。
5. 用户点击候选城市。
6. 系统执行：
   - 加入保存城市列表
   - 将其设为当前活跃城市
   - 刷新图 1 和图 2
7. 用户回到详情页继续查看。

### 12.4 从已保存城市切换

1. 用户打开图 3。
2. 点击已保存城市卡片，如“成都”。
3. 当前活跃城市切换为“成都”。
4. 图 1 和图 2 同步更新。

## 13. 视觉与交互规范建议

### 13.1 风格方向

参考图 1、图 2、图 3，建议从当前深色玻璃态调整为更柔和的浅色卡片风格：

- 背景：浅蓝灰、低饱和
- 顶部天气头图：蓝色渐变条
- 图标：统一插画风或统一扁平风
- 圆角：大圆角，体现桌面轻盈感

### 13.2 字体层级

优先级建议：

- 当前温度：最大字号
- 城市名：次高
- 当前天气现象/高低温/风速等：中字号
- 小时与 7 日预报：中小字号

### 13.3 布局规范

- 所有点击区域不小于 44px
- 使用 `gap` 组织列表与分组，避免依赖零散 `margin`
- 24 小时预报建议横向滚动
- 城市侧栏建议固定宽度，不随详情内容抖动

### 13.4 动效建议

- 图 1 -> 图 2：淡入 + 轻微缩放
- 图 2 -> 图 3：侧栏滑入
- 切换城市：头部信息平滑更新

动效要轻，不要造成桌面端负担。

## 14. 设置页改造建议

当前设置页在“关怀提醒”中仅支持：

- 开关天气
- 输入单个城市
- 自动定位单个城市

### 14.1 首版建议

设置页保留为“天气功能总开关 + 兜底配置页”，不再承担主要城市切换入口。

建议保留：

- 天气模块启用开关
- 是否允许自动定位
- 当前默认城市摘要

建议删除或降级：

- 直接编辑 `weatherCity` 的输入框

### 14.2 新的设置职责

设置页更多承担：

- 是否启用天气模块
- 是否启用自动定位
- 是否允许显示多城市列表
- 是否在默认卡片显示 3 天或 5 天摘要

而具体城市操作尽量移到图 3 中完成。

## 15. 技术实现建议

### 15.1 是否新增 Tauri 窗口

不建议首版为图 2、图 3 新增独立 Tauri 窗口。

原因：

- 当前三窗口模型已经包含 `main / settings / notification`
- 新增天气详情窗口会增加：
  - 窗口生命周期管理
  - 透明窗口点击穿透处理
  - 聚焦与层级问题
  - 关闭同步问题
- 这些复杂度与本需求的产品收益不匹配

结论：

- 图 2、图 3 建议都作为 `main` 窗口内的 React 浮层实现。

### 15.2 建议的数据流

```text
storage.ts
  -> weather preferences

weatherService.ts
  -> geocode / search / current / hourly / daily / bundle

Wall.tsx or weather container
  -> 控制 detail open / drawer open / active city

Weather UI components
  -> 只负责展示与事件回调
```

### 15.3 建议的本地持久化内容

需要持久化：

- 是否启用天气模块
- 当前活跃城市
- 已保存城市列表
- 上次自动定位城市
- 可选的最近访问时间

不建议持久化：

- 详情窗口是否打开
- 城市侧栏是否打开
- 当前搜索关键词
- 实时天气响应数据

## 19. 风险点与注意事项

### 19.1 城市搜索精度

Open-Meteo geocoding 能用，但中文城市搜索、同名城市去重、行政区展示可能不够理想，需要设计候选文案，例如：

- 城市名
- 省/州
- 国家

### 19.2 小时级数据长度

未来 24 小时数据量较大，如果全部平铺，界面容易挤压，需要提前决定：

- 显示 12 小时还是 24 小时
- 是否横向滚动

### 19.3 多城市摘要数据请求量

图 3 若同时展示多个城市小卡片，会带来额外请求量。建议：

- 已保存城市只取轻量摘要
- 做缓存
- 切换当前城市时才拉取完整详情

### 19.4 自动定位与手动城市优先级

必须明确：

- 当用户已经手动选过城市时，不应该被自动定位覆盖
- 自动定位更适合作为首次兜底

建议规则：

- 首次无城市时使用自动定位
- 用户手动选择后，以手动选择为主

## 20. 建议的最终方案结论

综合当前项目结构和你的目标效果，建议采用以下方案：

1. 不把此次需求直接做成独立 Widget 市场插件。
2. 继续基于现有 `WeatherCard` 内置模块升级。
3. 在 `main` 主窗口内部做：
   - 默认天气卡片
   - 天气详情浮层
   - 城市管理侧栏
4. 将天气配置从“单城市字符串”升级为“多城市列表 + 当前活跃城市”。
5. 将天气服务升级为“搜索 + 当前 + 小时 + 7 天 + 聚合”模式。
6. 分 4 到 5 个阶段逐步落地，先数据层，后 UI 层，再做体验细节。
